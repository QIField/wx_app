接口调用日志记录方案

覆盖「前端 → 后端 API」入站调用与「后端 → 中间方」出站调用，统一落库、可查询、可追溯；同时确立项目规范：现有功能与未来新功能的接口调用一律有日志。文末附组织管理方案（待确认后实施）。

wx_app · 微信消息工作台v1.02026-11-02评审中 · 待确认

1背景与目标

方案源于一次真实的排障过程：发送消息接口返回成功，消息却实际发送失败。

实测案例 · 2026-11-02 发送闭环排查
  1. POST /api/conversations/70/messages 返回 {"code":0,"status":0} —— 前端看到"已入队"，以为成功；
  2. 真正的发送结果在 confirm_worker 轮询里，异常被静默吞掉只累计 retry_count；
  3. 最后靠临时在终端打印中间方原始响应才定位：中间方返回 ret:500 "设备已离线，appId:wx_DLcv5wC1xSL52e0Bf6c8o"。

这类问题不该依赖临时代码。本方案把"完整请求/响应可查"变成常驻基础设施：

  • 查得到：任何一次入站、出站调用的参数、响应、耗时、结果，按时间 / 用户 / 组织 / 路径 / uuid 检索；
  • 串得起：发送闭环从 API 请求 → send_task → 中间方下发 → 轮询确认，用 uuid 串联；
  • 不添乱：日志写失败不影响业务，敏感字段脱敏，定期自动清理；
  • 可延续：写成项目规范（docs/interface-log.md），新功能自动被覆盖，验收时"有日志"是完成标准之一。
与现有 audit_log 的分工：audit_log 记"业务动作"（谁重置了谁的密码，模块级，手动埋点）；本方案记"接口调用流水"（每一笔 HTTP 往返，钩子自动埋点）。两者互补，不互相替代。

2总体设计

两条日志链路，各一张表，均由统一入口自动记录。

浏览器 / 前端所有 /api 请求（带 token）
→
Flask before/after_request入站钩子：记录参数、响应、耗时
唯一实现点，新接口零代码接入
→
表 access_log入站流水（本次新增）
业务层 / 定时任务发送、同步、资料、确认轮询
→
adapter/client.call / call_download出站唯一出口（现状即如此）
在此埋点：请求参数 + 原始响应
→
表 middle_call_log出站流水（本次新增）

设计原则

  • 入口唯一，天然全覆盖：出站本来只允许走 adapter/client（docs/api.md 附录既定规则），埋一次点覆盖现有 5 个模块与未来全部新模块；入站用 Flask 全局钩子，同样一次覆盖。
  • 快照而非外键：user_name / org_name 存快照字符串（与 audit_log 同款做法），账号停用后历史日志仍可读。
  • 失败不阻断：写日志包 try/except，异常只进 app logger（与 services/audit.log_action 同款兜底）。
  • 本地开发友好：开发库为 SQLite，模型用 SQLAlchemy 定义，MySQL DDL 仅作生产参考，两套等价。

3入站日志（前端 → 后端 API）

在 create_app 注册全局钩子，一次实现覆盖所有蓝图与未来新接口。

触发点

  • before_request：记起始时间、组装基本字段（user / org 从 request.current_user 取，未登录接口记空）暂存 flask.g；
  • after_request：补记响应码、耗时，落库一条 access_log；
  • teardown_request：请求抛异常时兜底补一条（result=fail，error_msg=异常摘要）。
实现要点 · backend/app.py（示意）
def register_access_log(app):
    @app.before_request
    def _t0():
        g.log_start = time.time()

    @app.after_request
    def _log(resp):
        # 豁免：健康检查 / WebSocket 握手 / 静态资源 / OPTIONS 预检
        if request.path in EXEMPT or request.method == "OPTIONS":
            return resp
        user = getattr(request, "current_user", None)
        AccessLog(
            access_time=datetime.now(), path=request.path, method=request.method,
            url=request.url, ip=_client_ip(), user_agent=request.user_agent.string,
            args=json.dumps(request.args.to_dict(), ensure_ascii=False),
            form=mask(json.dumps(request.get_json(silent=True) or request.form.to_dict())),
            user_id=user.id if user else None,
            user_name=user.name if user else "",
            org_id=user.org_id if user else None,
            status_code=resp.status_code,
            duration_ms=int((time.time() - g.log_start) * 1000),
        )
        db.session.commit()   # 独立提交；整体包 try/except，失败仅 warning
        return resp

豁免清单

/api/health（探活会刷屏）、/ws（WebSocket 握手）、静态资源、OPTIONS。媒体接口 /api/messages/<id>/media 不豁免——媒体加载失败也是排障对象，但 304 缓存命中照记（体积极小）。

脱敏规则（出入站通用）

  • 参数键名命中 password / old_password / new_password / token / authorization → 值替换为 ***；
  • 出站响应体超过 2000 字符截断并加 …(truncated)；
  • 媒体二进制不落内容，只记 http_status + content_type + 字节数。

4出站日志（后端 → 中间方）

在 adapter/client.py 的 call() 与 call_download() 内埋点——这两个函数已是全项目对中间方的唯一出口。

记录点（含异常，四类全覆盖）

场景successerror_msg 记录内容
正常返回 code=01空；response_body 存原始返回（截断）
业务失败 code!=0 / ret!=2000中间方 msg（如「设备已离线，appId:xxx」），ret 单独成列便于筛选
HTTP 层失败（超时/连接拒绝/5xx）0RequestException 摘要 + http_status（如有）
响应非法 JSON0ValueError 摘要 + 原始文本前 500 字符
埋点位置 · adapter/client.py（示意，包裹现有逻辑）
def call(module, action, params=None, uuid=None, openid=""):
    t0 = time.time()
    try:
        body = _do_call(...)          # 现有请求+解析逻辑
        log_middle(module, action, form, resp=body, ret=_pick_ret(body),
                   duration_ms=..., success=True, uuid=form["uuid"], openid=openid)
        return body
    except MiddleApiError as exc:
        log_middle(module, action, form, success=False, error=str(exc),
                   duration_ms=..., uuid=form["uuid"], openid=openid)
        raise

uuid 串联发送闭环

下发与确认轮询使用同一个 uuid（现状即如此，SendTask.uuid）。排查时一条链查全：

环节去哪查关键字段
1 前端发起access_logpath=/api/conversations/70/messages，user / org / form
2 中间方下发middle_call_logaction=post_text_message，uuid
3 轮询确认middle_call_logaction=get_post_text_message，同 uuid → ret=500 设备已离线
4 状态落库audit_log（SYNC 模块，已有）「发送确认失败」detail

5表结构 DDL

在参考表基础上增加：用户（快照）、组织（快照）、响应与耗时（排障关键）。开发库 SQLite 同构建模，以下为生产 MySQL 版。

入站接口访问日志
CREATE TABLE `access_log` (
  `id`          bigint NOT NULL AUTO_INCREMENT COMMENT '自增主键',
  `access_time` datetime NOT NULL COMMENT '访问时间',
  `user_id`     bigint COMMENT '登录账号 id；空=未登录接口',
  `user_name`   varchar(64) NOT NULL DEFAULT '' COMMENT '操作人姓名快照',
  `org_id`      bigint COMMENT '所属组织 id；空=未登录/开发者跨组织',
  `org_name`    varchar(64) NOT NULL DEFAULT '' COMMENT '组织名快照',
  `path`        varchar(255) NOT NULL COMMENT '请求路径',
  `method`      varchar(16) NOT NULL COMMENT 'GET/POST等',
  `url`         text NOT NULL COMMENT '完整请求url',
  `ip`          varchar(64) NOT NULL COMMENT '客户端IP',
  `user_agent`  text COMMENT 'UA客户端标识',
  `args`        text COMMENT 'GET参数json(脱敏)',
  `form`        text COMMENT 'POST参数json(脱敏)',
  `status_code` smallint NOT NULL COMMENT '响应HTTP状态码',
  `duration_ms` int NOT NULL DEFAULT 0 COMMENT '服务端耗时毫秒',
  `created_at`  timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_access_time` (`access_time`),
  KEY `idx_user` (`user_id`),
  KEY `idx_org` (`org_id`),
  KEY `idx_ip` (`ip`),
  KEY `idx_path` (`path`(191))
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='入站接口调用日志表';
出站中间方调用日志
CREATE TABLE `middle_call_log` (
  `id`             bigint NOT NULL AUTO_INCREMENT COMMENT '自增主键',
  `call_time`      datetime NOT NULL COMMENT '调用时间',
  `trigger_source` varchar(64) NOT NULL DEFAULT '' COMMENT '触发来源：请求路径或定时任务job名',
  `user_id`        bigint COMMENT '发起用户(请求上下文)；定时任务为空',
  `module`         varchar(32) NOT NULL COMMENT 'send_api/messag_api/login_api等',
  `action`         varchar(64) NOT NULL COMMENT '如 post_text_message',
  `uuid`           varchar(64) NOT NULL COMMENT '本次调用唯一标识，串联下发与确认',
  `openid`         varchar(64) NOT NULL DEFAULT '' COMMENT '设备标识',
  `request_params` text COMMENT '请求参数json(脱敏)',
  `http_status`    smallint COMMENT 'HTTP状态码；网络异常为空',
  `resp_code`      int COMMENT '中间方业务code',
  `ret`            int COMMENT 'processing_result.ret；仅查询类有',
  `response_body`  text COMMENT '原始响应(截断2000字符)',
  `duration_ms`    int NOT NULL DEFAULT 0 COMMENT '耗时毫秒',
  `success`        tinyint NOT NULL DEFAULT 1 COMMENT '1成功 0失败',
  `error_msg`      varchar(255) COMMENT '失败原因',
  `created_at`     timestamp NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_call_time` (`call_time`),
  KEY `idx_uuid` (`uuid`),
  KEY `idx_action` (`module`,`action`),
  KEY `idx_success` (`success`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='出站中间方调用日志表';

7项目规范条款

落地为 docs/interface-log.md（与 docs/audit-log.md 并列），条款如下，评审通过后即刻生效：

  1. 入站全量自动记录：Flask 钩子统一实现，任何新接口零代码接入；禁止在业务代码里手写访问日志。
  2. 出站唯一出口：对中间方的所有请求必须经 adapter/client.call / call_download，禁止在业务代码直接 requests.*；新增模块、新 action 无需额外埋点。
  3. 完成标准：新功能验收时，"在 access_log / middle_call_log 能查到该功能的调用记录"是完成标准之一；现有功能随 P0/P1 上线即自动覆盖。
  4. 写失败不阻断业务：日志环节整体 try/except，失败仅 app.logger.warning。
  5. 脱敏与截断：password/token 类字段打码；响应体截断 2000 字符；媒体二进制只记元信息。
  6. 保留期 90 天：并入现有每日 3:30 清理任务（audit_log 维持 180 天不变）。
  7. 分工边界：audit_log = 业务动作审计（手动埋点、模块枚举）；access_log / middle_call_log = 接口调用流水（自动、全量、排障用）。互不替代。

8组织管理 已确认方案 A · 待实施

2026-11-02 评审结论：采用方案 A（仅归属标记）——组织只是账号属性与检索维度，业务数据互通；暂缓实施，以下保留 A/B 说明供回溯。

共同部分（两个方案都做）

  • 新增 org 字典表，种子固定五条：佛山、珠海、中山、东莞百业、东莞合峰；本期不做组织增删改界面（固定字典），后续要扩展再加；
  • user 表加 org_id；新建账号必须选择组织（后端校验非空），编辑可改，停用不删；
  • 前端「账号管理」表单增加组织下拉（数据来自 GET /api/orgs），列表加组织列与筛选；
  • dev 开发者账号不绑组织（跨组织），引导创建逻辑不受影响；
  • access_log / 审计日志带组织维度，可按组织检索操作记录。
方案 A · 仅归属标记 未选择
  • 组织只是账号属性与检索维度；
  • 会话、消息、联系人等业务数据全部账号互通（现状不变）；
  • 改动面最小：user 表 + 账号接口 + 前端表单。
适合：组织先立起来，数据权限以后再说。
方案 B · 数据按组织隔离 未选择
  • agent 只能看到本组织账号所绑设备的会话 / 消息 / 联系人（归属链：user.open_id → 设备 → 会话）；
  • admin 管理本组织账号与数据；developer 跨组织；
  • 会话/联系人列表接口增加组织过滤，发送、撤回等写操作同样校验归属。
影响面更大：多个列表接口 + 写接口权限校验 + 回归测试。
