插件架构总览

Mutex Protocol · 群聊维度互斥控制 · 多设备自动报价防重

问题背景

现有快捷报价系统的消息同步按 设备维度独立运行：每台绑定的设备各自拉取消息、各自触发自动报价。当多台设备账号同时加入同一个企业微信群时，同一条客户询价会被 N 次重复处理 → 向群里发出 N 条重复报价。

本插件的目标：同一时间、同一群，只有一台设备能执行自动报价；其余设备静默丢弃，彻底杜绝重复。

for saved in pushed:
    if saved["direction"] == Message.DIR_IN:

        # ===== 新增：互斥锁拦截（3 行）=====

        if not should_process(saved["conversation_id"]):

核心模块详解

01 LockManager — 互斥锁管理

基于 Redis SET key value NX EX 30 实现的分布式互斥锁。锁按 群聊 wxid 隔离（粒度：每群一把锁），锁 value 包含 {device_id, term, timestamp}。TTL 默认 30 秒，Leader 每 10 秒续租一次。

方法说明返回值
try_acquire(group_wxid, device_id, term)尝试抢锁（SET NX）bool
renew(group_wxid, device_id, term)Leader 续租（GET+SET 原子校验 owner）bool
release(group_wxid, device_id, term)主动释放（Lua 脚本校验 owner）bool
peek(group_wxid)读锁内容（不修改）dict | None

02 DeviceMonitor — 账号状态检测

双重健康检测：Redis 心跳（每 10s） + 设备在线状态（复用已有 check_device_online）。连续 3 次续租失败 → 本地降级为被动模式；离线设备自动被排除出选举候选池。

10s
Leader 每 10 秒写一次 Redis key
锁 TTL
30s
3 个心跳周期的容错窗口
失效判定
3×
连续 3 次续租失败 → 降级

03 ElectionEngine — 群聊维度选举

Leader 失效时，下一条消息触发选举：所有候选设备同时 SET NX 抢锁，Redis 原子性保证只有一个成功。选举胜出者获得新任期号 term + 1，自动接管自动报价职责。败者读取锁的新 owner → 静默降级。

选举触发条件（OR）：

  • Redis 锁已过期（TTL 到了）
  • 本地心跳连续 3 次失败（自己可能脑裂了）
  • 锁存在但 owner 的 lease 已过期 60s+（极端情况）

04 ConflictResolver — 冲突规避策略

核心机制：任期号 fencing token。每个 Leader 任期递增，所有操作携带当前 term。当网络分区恢复后，旧 Leader 即使仍认为自己持有锁，一旦发现 Redis 中的 term 大于自己的，立即降级。

策略解决问题实现
任期号 fencing脑裂后双 Leader所有 Redis 写入带 term 校验
lease + 主动降级网络分区时假 Leader3 次续租失败立即停止报价
设备在线筛选离线设备误参与选举复用 pollable_devices() 排除离线
单机锁 + 分布式锁进程重启后瞬时竞争本地 threading.Lock 保护抢锁临界区
