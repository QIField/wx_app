L1 · LockManager 单元测试

UT-LOCK-001：SET NX 成功获取锁
Given: 锁不存在 When: try_acquire("grpA", "dev_01", 1) Then: return True + Redis key 存在 + value.owner="dev_01"
  • 断言返回 True
  • 断言 Redis key 存在
  • 断言 value.owner == "dev_01", term == 1
  • 断言 TTL ≈ 30s
UT-LOCK-002：SET NX 失败 — 锁已被别人持有
Given: 锁已存在 owner="dev_01" When: try_acquire("grpA", "dev_02", 2) Then: return False + 原锁内容不变
UT-LOCK-003：自己可以续租自己的锁
Given: 锁存在 owner="dev_01", term=1 When: renew("grpA", "dev_01", 1) Then: return True + TTL 被续到 30s
UT-LOCK-004：别人的锁不能续租
Given: 锁存在 owner="dev_01", term=1 When: renew("grpA", "dev_02", 1) Then: return False + 锁不变
UT-LOCK-005：term 不匹配不能续租（fencing token）
Given: 锁存在 owner="dev_01", term=5 When: renew("grpA", "dev_01", 4) ← term 落后 Then: return False + 锁不变

L2 · DeviceMonitor 组件测试

UT-MONITOR-001：心跳续租 3 次失败 → 自动降级
Given: DeviceMonitor("dev_01") promote("grpA", term=1) When: lock_manager.renew() 连续 3 次返回 False Then: 60s 内（3 × 20s 测试加速）is_leader("grpA") 返回 False
UT-MONITOR-002：心跳恢复 → failures 计数归零
Given: 已连续失败 2 次 When: 第 3 次心跳成功 Then: state.failures == 0

L3 · 多进程集成测试（双 Leader 绝对不允许）

IT-MUTEX-001：多进程同时 should_process → 最多一个 True
核心红线测试 4 个进程并发启动 重复 100 次

场景：启动 4 个子进程，每个进程序 should_process("grpA") 10 次，每次间隔 50ms。

断言：每一轮中，返回 True 的进程数 ≤ 1。如果任何一轮出现 2 个以上 True → 测试失败 = 插件存在致命 bug。

覆盖率：必须运行 100 次以上，每次用不同的 Redis key 隔离。

IT-MUTEX-002：Leader 离线 → 选举 → 新 Leader 接管
进程 A 当选 → Kill A 等 35s（TTL 到期） 进程 B 下一条消息到来
  • 断言 35s 后 Redis lock key 消失
  • 断言 B 的 should_process 返回 True
  • 断言 term 被提升
  • 断言后续其他进程的 should_process 返回 False
IT-MUTEX-003：脑裂恢复测试 — 低任期 Leader 必须降级
Leader A (term=5) + 分区 Leader B (term=6) 当选 分区恢复

A 恢复连接后，should_process 必须立即返回 False —— 即使 A 本地还以为自己是 Leader。

L4 · 故障注入测试（Chaos Engineering）

CHAOS-001：Redis 不可用 30s → 恢复
Leader A 正常工作 Kill Redis 30s 恢复 Redis

验证 Redis 恢复后状态自洽：锁没有丢失、term 没有混乱、Follower 不会趁机夺权。

CHAOS-002：选举风暴 — 8 台设备同时启动
清理所有锁 同时启动 8 个进程 全部 should_process

重复 50 次。每次必须恰好有一个 Leader 当选，且后续 7 个稳定静默。

CHAOS-003：Leader 在选举中途崩溃
A 抢锁成功 Promote 刚返回 True A 立即崩溃

验证 30s 后其他进程能正确接管，且不会出现 A 的残留状态影响新选举。

灰度上线计划

阶段持续覆盖范围关键指标
Phase 1 Shadow 模式 3 天 1 台测试设备 should_process 只打日志不拦截 —— 验证选举逻辑正确
Phase 2 试点 5 天 2~3 台生产设备（非关键群） 对比启用前后的报价条数 —— 确认重复从 N 降到 1
Phase 3 全量 持续 全部设备 监控 Redis 锁健康度 · 心跳超时率 · 选举频率
