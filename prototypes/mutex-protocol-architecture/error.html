异常处理与故障兜底

8 种典型故障场景 · 插件如何自恢复

设计原则

核心原则
永不阻断业务
插件任何异常 → 兜底放行 → 原始业务照常执行
防双 Leader
任期 fencing
所有 Redis 写入带 term 校验，过期锁无法重新生效
防全失效
TTL 兜底
极端情况也不会出现所有设备都不报价（插件宕机 → 放行）

故障场景矩阵

E01 Leader 设备离线（正常）

故障类型可恢复 进程消失 / 网络断开
检测手段Redis 锁 TTL 到期（30s）+ 心跳连续失败
自动恢复✅ 锁过期 → 下一条消息触发选举 → Follower 自动接管
业务影响最长 30s ~ 60s 的报价延迟（取决于消息到达时机）
极端恶化🔴 不会发生 — 锁到期后必有一台设备抢锁成功

E02 Redis 短暂不可用（网络抖动）

故障类型可恢复 Redis 连接超时 / 短暂断连
检测手段try_acquire / peek / renew 抛异常
自动恢复✅ 异常兜底：should_process() 返回 True（放行） → 每台设备都执行报价？
业务影响⚠️ 短时 Redis 不可用 = 所有设备都放行 = 可能重复报价
缓解措施本地缓存最后一次 Leader 状态，Redis 挂了时先查本地 → 只有心跳超时才放行
python · 本地缓存兜底逻辑 
# should_process 中，Redis 异常时的处理
try:
    lock = _lock_manager.peek(group_wxid)
except RedisConnectionError:
    log.error("Redis 不可用，查本地缓存兜底")
    # 不是立即放行 —— 先看本地是否记录过自己是 Leader
    if _device_monitor.is_leader(group_wxid):
        return True   # 本地记得自己是 Leader，放行
    else:
        return False  # 本地记得自己是 Follower，静默（防重复）
except Exception as exc:
    log.exception("未知异常，兜底放行")
    return True  # 最后的安全网

E03 网络分区（脑裂）

故障类型严重 设备分区成两组，各自有 Redis
检测手段续租连续失败 + 恢复后 term 比对
自动恢复✅ fencing token：分区恢复后，低任期号的 Leader 立即降级
业务影响分区期间两边各自报价 → 重复（但边界很窄：必须两边都有 Leader + 都有客户询价）
缓解措施单 Redis 实例 + Leader 连续 3 次心跳失败主动降级（宁可漏处理，不发重复）

E04 选举风暴（同时有大量设备上线）

故障类型性能 多台设备同时 SET NX
检测手段Redis 命令执行频率突增
自动恢复✅ Redis SET NX 原子性保证：N 台设备同时抢，只有 1 台成功 → 其余 N-1 台失败后读 winner
业务影响几乎无影响 —— 选举就是为这种场景设计的
优化失败后可以加 50ms ~ 200ms 随机抖动再重试（避免热循环）

E05 Redis 锁被误删（运维 / 过期）

故障类型可恢复 锁意外消失
检测手段Leader 续租失败 + peek 返回 None
自动恢复✅ Leader 发现锁没了 → 重新 SET NX → 大概率抢回自己的锁
业务影响可能产生一次额外选举，但不会重复（选举期间只有一台能抢到）

E06 插件自身 Bug 导致异常

故障类型代码 新引入的 bug 导致崩溃
检测手段异常日志 + should_process 兜底逻辑
自动恢复✅ should_process 所有异常兜底返回 True —— 插件 crash = 无互斥 = 回到插件安装前的状态
业务影响降级为多设备独立报价（可能重复），但 核心业务不会中断
缓解措施灰度发布：先在 1 台设备启用 → 观察 1 天 → 逐步扩量

E07 所有设备全部离线

故障类型极端 全部设备都断了
检测手段pollable_devices() 返回空
自动恢复❌ 无法自动恢复，需人工
业务影响整条链路挂了 —— 这不是插件问题，是上游中间方/网络挂了
缓解措施插件的故障处理到此为止，应该由中间方/网络层处理

E08 时钟漂移（设备间时间不一致）

故障类型边缘 设备本地时间不准
检测手段Redis server time 对比
自动恢复✅ 插件所有时间基准用 Redis 服务器时间，不用设备本地时间
业务影响无影响 —— SET NX + EX 的原子性完全在 Redis 侧保证

防御深度：多层兜底机制

层级机制防什么失败后的退化
L1 原子锁 Redis SET NX EX 并发抢锁 → 双 Leader ↓ 退到 L2
L2 任期 fencing term 号只升不降 脑裂恢复后旧 Leader 复活 ↓ 退到 L3
L3 心跳续租 10s 续租 · 3 次失败降级 假 Leader（网络分区内） ↓ 退到 L4
L4 TTL 兜底 30s 自动过期 Leader 消失后锁永远不释放 ↓ 退到 L5
L5 本地缓存 Redis 挂了看本地状态 Redis 短暂不可用时重复报价 ↓ 退到 L6
L6 异常放行 should_process 兜底 True 插件自身 Bug 阻断业务 退化为"无插件"状态
